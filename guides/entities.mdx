<Note>
  Entity delivery is staged by model and account. Saving a kind does not mean every model can use it. Check the model's `entityReferences` and your authenticated `/entities/capabilities` before uploading inputs. Generic SDK selections require `@modelrunner/client` 1.5.0+ or `modelrunner-ai` 0.8.0+. Existing character-only integrations keep working with their character-v1 capability and earlier supported SDK versions.
</Note>

An Entity is a saved reference bundle of one to twenty owned images. Its kind is **character**, **prop**, **environment**, **style** or **scene**. Saving it does not train a model or run generation. Models use the selected images, or the visual description in description-only mode, according to their advertised capabilities.

## In the playground

1. Open **Assets**. Choose Characters, Props, Environments, Styles or Scenes in the library sidebar, then **New**. The Home page also has an Entities panel with Add shortcuts.
2. Upload/drop images, browse your owned Assets, or import a public HTTPS URL. Successful imports become owned Files. Set a name and identifier such as `lantern`; add a visual description. Characters require a description; other kinds may leave it empty.
3. Reorder defining images and choose a member image as the cover. Characters can also use a separate display cover. The **first ordered image** remains the default prompt reference; a separate cover is never implicitly sent to inference.
4. On a supported model, type `@` and select an Entity beside the caret. Suggestions show its cover, name and kind. Bound handles are underlined. Inspect a handle to read its description, check delivery mode and choose reference images for this run. The picker shows supported kinds admitted for your account.
5. Choose **Preview reference input** to inspect the final prompt, ordered images and remaining capacity. Preview does not submit a job or charge. **Run** checks the selection again and submits once.

Only explicitly selected mentions resolve. A plain `@lantern`, an email or a URL remains ordinary text. Repeated mentions reuse the selected references. Manual images retain their order and duplicates; selected images append in first-mention order and reuse an existing position when their URL is already present. Oversized selections are refused rather than truncated.

Kinds and character identifiers are fixed. Other identifiers may be edited; the entity ID and historical snapshots stay the same. Updating descriptions, identifiers, covers or defining images increments the saved version; favorites, tags and organization links do not; a stale selection must be refreshed. Changes to the library do not rewrite an accepted run. Opening your own referenced run restores the prompt you submitted, including its selected `@handles`, and checks the recorded references against your current library. Changed versions, removed images or unavailable entities require review before **Run** submits your visible edits. **Reset** restores the original prompt and selections. **Run previous input** is a separate action: it repeats the saved resolved input, ignores edits in the form, and works independently of changes to your library. It starts a new charged run; results may differ. Expand **Resolved model input** to inspect the saved values. Public examples continue to use expanded input without private bindings.

Description-only delivery requires a nonempty visual description and does not send the saved reference images. When a selected entity lacks a description, Run is blocked. Choose **Add description** to save one and explicitly refresh that selection without losing the prompt, choose a compatible image-reference model, or remove the mention. A non-character Entity without a description can still use a supported image-list model. Library editing may be paused independently of running already saved references.

## Model and account discovery

Use the account's API key with `Authorization: Key <key>` on `https://modelrunner.run`.

`GET /models/{owner}/{alias}` advertises a safe capability:

```json
{
  "entityReferences": {
    "contractVersion": 1,
    "enabled": true,
    "previewEnabled": true,
    "mode": "image-list",
    "promptField": "prompt",
    "supportedKinds": ["character", "prop"],
    "maxEntities": 4,
    "imageField": "images",
    "maxImages": 8,
    "maxImagesPerEntity": 2
  }
}
```

This is an illustrative response; read your actual model's metadata. Preview availability is separate from enabled submission. Missing generic metadata, an unknown contract version, or a selected kind absent from `supportedKinds` means generic delivery is unavailable. Model support never follows from an image field's existence alone.

`GET /entities/capabilities` requires the concrete account identity:

```json
{
  "contractVersion": 1,
  "writesEnabled": true,
  "submissionsEnabled": true,
  "newKindsEnabled": true
}
```

Creation/editing requires `writesEnabled`; non-character creation/editing also requires `newKindsEnabled`. Non-character submission requires both submission admission and a matching enabled model capability. Reads/deletion remain available for cleanup when new-kind admission is disabled. SDKs check model support and account eligibility before transforming/uploading inputs. Character-only calls retain the existing `characterReferences.contractVersion: 1` handshake and do not require new-kind admission.

## Entity library API

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/entities?q=&type=prop&page=1&limit=24` | Owner search/filter/pagination; five-kind counts follow owner/search scope while type filters items. |
| POST | `/entities` | Create using owned ready File IDs. |
| GET | `/entities/{id}` | Read metadata, version and ordered image references. |
| PATCH | `/entities/{id}` | Update using the expected `version`. |
| DELETE | `/entities/{id}` | Remove the library entry; retain its Files and historical Requests. |
| POST | `/entities/check-handle` | Check an identifier, or suggest/check one from a name. |
| POST | `/entities/import-image` | Import a public HTTPS raster image into an owned File; body contains `type` and `url`. |
| POST | `/entities/validate-images` | Check stored reference readiness; body contains `type` and `fileIds`. |
| GET | `/entities/{id}/usage?page=1` | Paginated owner-only history of automatic reference use. |
| GET | `/entities/{id}/assets` | Combined generated/manual media, deduplicated before pagination. |
| PUT / DELETE | `/entities/{id}/assets` | Link/unlink owned media with `{ "fileIds": [...] }`; unlink preserves recorded generation usage. |
| PUT / DELETE | `/entities/{id}/favorite` | Set/remove a favorite without changing reference version. |
| POST / DELETE | `/entities/{id}/tags` / `/entities/{id}/tags/{tagId}` | Assign an owned tag by ID/name or remove its assignment. |
| GET | `/entities/capabilities` | Read account rollout/write/submission admission. |
| POST | `/entities/preview` | Resolve a bound direct-model input without inference. |

Example create body, replacing the File UUID with your own upload/import result:

```json
{
  "type": "prop",
  "name": "Brass lantern",
  "handle": "lantern",
  "description": "Brass lantern with dented glass and a worn leather strap",
  "fileIds": ["22222222-2222-4222-8222-222222222222"],
  "coverFileId": "22222222-2222-4222-8222-222222222222"
}
```

Names are bounded to 128 characters. Handles use `[a-z][a-z0-9_-]{0,63}`, are unique across your kinds, and exclude positional identifiers such as `image1`. Images must be ready, owned static raster Files, at most 20 MiB and 40 megapixels each. The existing `coverFileId` must remain an original member image. Characters may additionally set nullable `displayCoverFileId`; responses include optional `displayCover`. Prefer the display cover for presentation, while keeping defining `files` and inference selections separate. Another account's public image URL does not grant ownership of its File.

`PATCH` includes the current version, for example `{ "version": 2, "description": null }` to clear a non-character description. A concurrent edit returns 409. Missing and foreign IDs both return 404.

Create is one POST with no automatic retry. If its outcome is uncertain, inspect owner search/read results and compare the attempted content before another create. The API does not promise durable create idempotency.

### Typed library clients

Use the JS `entities` client or the Python library helpers with your own ready File IDs.
The following examples assume the configured clients from the submission examples below.

```javascript
const { items, counts } = await modelrunner.entities.list({ type: "prop" });
const { handle, available } = await modelrunner.entities.checkHandle({ name: "Brass lantern" });
const entity = await modelrunner.entities.create({
  type: "prop", name: "Brass lantern", handle,
  fileIds: [ownedFileId], description: "Brass body and a red leather strap",
});
const updated = await modelrunner.entities.update(entity.id, {
  version: entity.version, description: "Brass body and a blue leather strap",
});
// await modelrunner.entities.get(entity.id);
// await modelrunner.entities.delete(entity.id);
```

```python
items = modelrunner_ai.list_entities(type="prop")
availability = modelrunner_ai.check_entity_handle(name="Brass lantern")
entity = modelrunner_ai.create_entity({
    "type": "prop", "name": "Brass lantern", "handle": availability["handle"],
    "fileIds": [owned_file_id], "description": "Brass body and a red leather strap",
})
updated = modelrunner_ai.update_entity(entity["id"], {
    "version": entity["version"], "description": "Brass body and a blue leather strap",
})
# modelrunner_ai.get_entity(entity["id"])
# modelrunner_ai.delete_entity(entity["id"])
```

Library helpers use owned ready File IDs. The API remains responsible for readiness,
ownership, kind admission and version checks. Writes are single attempts and refuse
redirects; after an uncertain create, reconcile owner reads before creating again.
Deleting an Entity keeps its Files and historical Requests. Missing update fields
are preserved; a conflicting version returns 409. Check availability before create,
while still handling a concurrent conflict. Availability does not reserve a handle.

Python also exposes these methods on `SyncClient` and `AsyncClient`, with module-level
`_async` variants. Read admission through JS `entities.capabilities()` or Python
`get_entity_capabilities()`. These helpers require the new SDK versions above.

## Preview and queue submission

The explicit binding array stays the same reserved wire key. Send this body to `POST /entities/preview`:

```json
{
  "endpoint": "your-team/image-editor",
  "input": { "prompt": "@lantern on a wooden table" },
  "modelrunner_references": [{
    "type": "prop",
    "id": "11111111-1111-4111-8111-111111111111",
    "mention": "lantern",
    "version": 1,
    "file_ids": ["22222222-2222-4222-8222-222222222222"]
  }]
}
```

Replace the endpoint and IDs with a model and Entity admitted for your account. The response includes `effectiveInput`, typed `entities`, mode/config version, image counts and remaining capacity. Omitting `file_ids` selects the first saved image; an explicit list preserves that selection order. Preview freezes nothing for a later job, so submission revalidates ownership, kind, version, membership and availability.

To submit through HTTP, put ordinary model fields and the same `modelrunner_references` array together at the root of `POST https://queue.modelrunner.run/{owner}/{alias}`. The preview's outer `input` wrapper belongs only to the preview endpoint. Bindings never become provider/model input.

### JavaScript

```ts
import { modelrunner } from "@modelrunner/client";

const request = await modelrunner.queue.submit("your-team/image-editor", {
  input: { prompt: "@lantern on a wooden table" },
  references: [{
    type: "prop",
    id: "11111111-1111-4111-8111-111111111111",
    mention: "lantern",
    version: 1,
    file_ids: ["22222222-2222-4222-8222-222222222222"],
  }],
});
```

`subscribe` accepts the same `references` option. `EntityReferenceBinding` and `EntityKind` are exported types; character-specific types remain available.

### Python

```python
import modelrunner_ai

request = modelrunner_ai.submit(
    "your-team/image-editor",
    arguments={"prompt": "@lantern on a wooden table"},
    entity_references=[{
        "type": "prop",
        "id": "11111111-1111-4111-8111-111111111111",
        "mention": "lantern",
        "version": 1,
        "file_ids": ["22222222-2222-4222-8222-222222222222"],
    }],
)
```

`submit_async`, sync/async `subscribe`, `SyncClient` and `AsyncClient` accept the same option. `character_references` remains character-only; pass one reference option per call. `EntityReferenceBinding` and `EntityKind` are exported.

Both SDKs copy selections before asynchronous work, negotiate support before uploads and attempt the referenced POST once. They do not retry it after a timeout or redirect. Polling retains normal retries. After an uncertain submission, check history or contact support with its request ID; do not replay it automatically.

## History, visibility and limits

Owner responses retain authored input and a bounded `entityReferences` summary with `effectiveInput`; character history retains its compatible summary. Public examples use ordinary effective input without private library bindings. Publishing a referenced run exposes the expanded prompt/descriptions and selected image URLs; the private library does not hide those intentionally published contents.

The [character API](/guides/characters) stays character-only. Chat/Messages, wrappers and GPU deployments do not accept bindings in this release. Assisted image/description generation, editable identifiers, independent covers, manual galleries and entity favorites are outside this release. Per-model reference semantics and visual consistency depend on that model; library kinds are not a promise of universal support.


## Organize entities and their media

Open an entity card to see its associated-media gallery with a reference and
description inspector. **Generated with this entity** records automatic use;
**Manually linked** records an organization link. An item can have both. Removing
its manual link keeps the recorded usage. Linking media never changes defining
references. **View all runs** includes pending or failed runs with no media.

Entity tags and favorites use the same private tag registry as media. They do
not change inference versions. [Private asset collections](/guides/assets)
organize files independently of the public model catalog.

The added organization SDK methods require `@modelrunner/client` 1.6.0+ or
`modelrunner-ai` 0.9.0+. Existing 1.5.0/0.8.0 library and reference methods remain
compatible.

```javascript
await modelrunner.entities.setFavorite(entity.id, true);
await modelrunner.entities.assignTag(entity.id, { name: "Campaign" });
await modelrunner.entities.linkAssets(entity.id, [ownedFileId]);
const gallery = await modelrunner.entities.listAssets(entity.id, { order: "newest" });
// gallery.items distinguish generated and manuallyLinked.
await modelrunner.entities.unlinkAssets(entity.id, [ownedFileId]);
```

```python
modelrunner_ai.favorite_entity(entity["id"])
modelrunner_ai.assign_entity_tag(entity["id"], {"name": "Campaign"})
modelrunner_ai.link_entity_assets(entity["id"], [owned_file_id])
gallery = modelrunner_ai.list_entity_assets(entity["id"], {"order": "newest"})
modelrunner_ai.unlink_entity_assets(entity["id"], [owned_file_id])
```
